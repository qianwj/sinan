# Sinan 需求基线

> **文档性质**：产品需求与验收基线，描述系统要解决的问题、服务对象和可观察结果。
> **非本文档内容**：分层、模块、数据库、事件、队列、运行时、第三方依赖和代码实现。
> **版本**：v0.1 ｜ **状态**：首期范围基线 ｜ **更新**：2026-09-02

## 1. 文档规则

### 1.1 需求与架构的边界

- 本文档回答 **为什么做、为谁做、做什么、何时算完成**。
- `architecture.md` 只能在本文档需求成立的前提下定义设计方案。
- 需求 ID 是跨文档追踪的唯一锚点；架构决策、模块设计和后续测试应引用对应 ID。
- 需求表达结果和约束，不规定实现方式。出现 SQL、代码、类名、具体查询、事务步骤或部署脚本时，应移出本文档。

### 1.2 评审规则

每次评审按以下顺序进行：

1. 先确认是否直接支持核心价值闭环，再讨论支撑能力和技术细节。
2. 每个设计结论必须能回指一个或多个需求 ID；无法回指的内容默认是候选想法，不进入基线。
3. 每条需求必须有可观察的验收条件，不能只写“高性能”“智能”“可靠”等口号。
4. 需求、方案、实现三者分离：用户目标和约束不能被某个当前方案冒充。
5. 任何需求变更都必须说明影响的需求版本、在途工作和验收条件；不能静默改变目标。
6. 队列、恢复、性能和运维问题按支撑优先级处理，不得遮蔽意图治理、需求血缘、协作收敛、注意力路由和先例复用。

### 1.3 优先级

| 标记 | 含义 |
|---|---|
| **P0** | 首期闭环必须具备；缺失则不能验证产品价值 |
| **P1** | 首期可用性和规模化协作需要；P0 稳定后实现 |
| **P2** | 后续增强；不阻塞首期闭环 |

优先级表示交付顺序，不表示实现难度。任何 P1/P2 能力都不能以牺牲 P0 的可解释性和人的最终控制权为代价。

## 2. 产品定义

### 2.1 产品目标

Sinan 面向一人公司，帮助一个人带领一支 AI agent 团队完成产品构建。系统把人的模糊意图逐步收敛为可审查、可交付的产出，并把必须由人判断的事项集中到少量、清晰的决策点。

核心价值闭环：

```text
意图 → 澄清与验证 → 版本化需求 → 任务协作
     → 产出验证与收敛 → 人的决策 → 交付
     → 决策与经验可复用
```

队列、执行器、持久化和恢复是保证闭环可信的支撑能力，不是产品目标本身。

### 2.2 首期用户与角色

| 角色 | 目标 | 权限边界 |
|---|---|---|
| **产品所有者** | 提出意图、确定目标、做最终取舍、批准交付 | 对需求、决策和对外发布拥有最终权威 |
| **AI agent** | 澄清、设计、实现、验证和互审 | 只能在授权任务和工作范围内行动，不能替代产品所有者做最终决策 |
| **系统** | 保存事实、协调协作、路由注意力、发现异常并恢复 | 不得隐式改变需求目标或把未确认的外部副作用当作成功 |

首期为单用户系统。agent 可以并行，但并行度服从人的审查能力，而不是以最大化并行数量为目标。

### 2.3 首期范围

首期覆盖产品、设计、开发、交付四段顺序价值链：

1. 产品：把意图澄清为目标、原因和验收条件。
2. 设计：用可运行原型验证交互和视觉方向。
3. 开发：在隔离的工作范围内实现需求并接受机器与 agent 闸门。
4. 交付：由产品所有者确认后发布，并能识别交付结果。

客服、市场、财务属于后续构建的产品能力，不属于首期自动执行范围。实际付款、签约、报税等不可逆外部动作首期由人工处理。

## 3. 核心用户场景

### S-01 提出并澄清意图

产品所有者可以用自然语言提出想法。系统帮助识别真实目标、原因、边界和可判定的验收条件；当输入已经预设实现方案时，系统必须先确认目标，而不是直接把方案当作需求。

**完成标志**：得到一份产品所有者可确认或驳回的需求草稿；草稿不能在未经确认的情况下进入执行。

### S-02 用原型验证方向

对交互或视觉不确定的需求，系统应支持快速生成可运行原型。产品所有者可以通过实际操作发现“不对”的地方，并把反馈关联回原始意图。

**完成标志**：原型能支持目标路径的体验判断；原型被接受、修改或丢弃都有明确结果，假数据不会被误认为生产能力。

### S-03 形成版本化需求

产品所有者确认后，系统记录需求目标、原因、验收条件和来源。后续修改必须形成可比较的新版本，并能说明修改原因。

**完成标志**：任何任务、决策和交付结果都能追溯到对应需求版本；查看需求时能区分当前目标与历史目标。

### S-04 派生和协作

系统根据已确认需求拆分可执行任务，标明任务与需求的关系、依赖和预期影响范围。多个 agent 可以并行工作，系统应提前暴露潜在的文件、接口或契约冲突。

**完成标志**：每个在途任务都有明确产出和完成条件；冲突在合并前可被发现；并行工作最终能收敛到可审查产物。

### S-05 自动验证与互审

任务产出应先经过适用的机器检查，再由 agent 进行独立互审。互审应围绕需求和验收条件，指出证据、风险和需要人判断的分歧。

**完成标志**：系统不会把“agent 声称完成”直接当作交付；验证失败、互审要求修改和需要升级的情况均有明确出口。

### S-06 人的决策与注意力路由

系统把阻塞工作、需求冲突、低置信度先例、未知副作用和交付确认集中展示，并按对交付的阻塞成本排序。产品所有者可以查看上下文、做出选择并看到选择的影响。

**完成标志**：用户无需遍历所有 agent 才能找到待处理事项；每个决策都有来源、选项、影响范围和处理结果。

### S-07 先例复用

系统应保存已经确认的决策、适用条件和结果。在相似场景中可以提供先例和证据；只有满足明确置信条件的先例才能自动采用，其余必须升级给产品所有者。

**完成标志**：用户能看到“为什么采用这个先例”；被否决的方案不会在相同条件下无提示地再次出现。

### S-08 需求变化与漂移控制

需求变化时，系统识别受影响的在途任务、验收条件和已有产出，并要求明确选择继续、重新派生、暂停或放弃。系统应能发现产出已经偏离原目标的情况。

**完成标志**：需求变化不会静默留下过时任务；漂移在合并或交付前进入可处理的决策项。

### S-09 交付与反馈

当所有必要工作满足验收条件后，系统向产品所有者呈现交付摘要、证据和剩余风险。发布后反馈可以关联到已交付需求，并用于后续需求或先例。

**完成标志**：一次交付有清晰的需求范围、验证证据、决策记录和可追踪反馈。

### S-10 本机故障后的继续工作

进程崩溃、机器异常重启、睡眠唤醒、网络中断或模型服务超时后，系统应能区分已确认、可重试和结果未知的工作。恢复后不得因为重复执行造成不可接受的副作用，也不得丢失已确认的需求、决策和审计事实。

**完成标志**：恢复后用户能看到继续执行、等待核对或需要重做的明确状态；未知结果不会被伪装成成功或失败。

## 4. 功能需求

### 4.1 意图与需求治理

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| REQ-INT-01 | 系统必须区分意图、目标、验收条件和实现方案。 | P0 | 输入包含具体方案时，仍能让用户确认它服务的目标；方案不能直接成为执行指令。 |
| REQ-INT-02 | 系统必须保留需求的原因（`why`）、目标、范围和不做事项。 | P0 | 用户查看需求时能同时看到这些内容，并能说明它们来自哪次确认。 |
| REQ-INT-03 | 需求进入执行前必须经过产品所有者确认。 | P0 | 未确认的草稿不会创建可执行工作；驳回结果可追溯。 |
| REQ-INT-04 | 需求必须支持版本化和版本间差异说明。 | P0 | 新版本不覆盖旧版本；系统能列出受影响任务和验收条件。 |
| REQ-INT-05 | 原型阶段的反馈必须能回到对应意图或需求。 | P0 | 接受、修改、否决原型都会产生可追溯的后续动作。 |
| REQ-INT-06 | 需求变更必须显式处理在途工作。 | P0 | 继续、重新派生、暂停、放弃等结果可区分，且不存在无主的旧任务。 |

### 4.2 任务与多 agent 协作

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| REQ-COL-01 | 每个任务必须关联需求版本、产出类型、完成条件和依赖。 | P0 | 任一任务都能回答“服务哪个目标、交付什么、依赖什么”。 |
| REQ-COL-02 | 系统必须支持多个 agent 在授权范围内并行工作。 | P0 | 并行任务彼此隔离；任一 agent 不能覆盖另一个 agent 未提交的工作。 |
| REQ-COL-03 | 系统必须在合并或交付前暴露潜在冲突。 | P0 | 文件、接口、共享契约冲突有明确状态和责任人。 |
| REQ-COL-04 | 共享契约必须有唯一责任方，其他 agent 通过提议和审查修改。 | P1 | 契约修改可追溯到提出者、批准者和受影响任务。 |
| REQ-COL-05 | 任务产出必须经过适用的自动检查和独立互审。 | P0 | 检查证据与需求验收条件绑定；失败或分歧不能直接进入交付。 |
| REQ-COL-06 | 系统必须支持任务暂停、重做、失败和放弃，并保留原因。 | P0 | 每种结果都能在任务历史中区分，不以删除记录代替状态处理。 |

### 4.3 决策与注意力

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| REQ-ATT-01 | 系统必须将需要产品所有者判断的事项集中到决策入口。 | P0 | 用户能从单一入口看到所有未解决的阻塞事项。 |
| REQ-ATT-02 | 决策项必须提供来源、上下文、可选动作、影响范围和证据。 | P0 | 用户无需阅读 agent 原始日志即可做出有依据的选择。 |
| REQ-ATT-03 | 决策项必须按阻塞成本和紧迫性排序。 | P0 | 排序变化有可解释原因；低价值信息不能长期遮挡高阻塞事项。 |
| REQ-ATT-04 | 产品所有者是需求和交付的最终权威。 | P0 | agent 不能绕过确认改变需求、批准交付或确认未知外部副作用。 |
| REQ-ATT-05 | 系统必须记录决策结果及其对任务、需求和交付的影响。 | P0 | 决策完成后可追踪哪些工作被继续、修改、暂停或放弃。 |
| REQ-ATT-06 | 系统必须记录真实的人类审查行为，用于衡量注意力成本。 | P1 | 能区分决策项被展示与被用户实际打开、处理的时间。 |

### 4.4 记忆与先例

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| REQ-MEM-01 | 系统必须保存已确认的决策、约定、事实和失败经验。 | P0 | 记忆包含来源、时间、适用范围和关联需求。 |
| REQ-MEM-02 | 系统必须支持按当前任务和需求上下文召回相关记忆。 | P0 | 召回结果能显示匹配依据，不能只返回无来源的结论。 |
| REQ-MEM-03 | 先例自动采用必须受置信度和适用条件约束。 | P0 | 低置信度、条件不满足或存在冲突时必须升级给人。 |
| REQ-MEM-04 | 人工决策完成后，系统必须能将决策事实沉淀为可复用先例。 | P1 | 后续相似场景能检索到该先例，并保留原决策证据。 |
| REQ-MEM-05 | 不同项目或用途的记忆必须具备边界，不能无提示混用。 | P1 | 召回结果显示适用范围；越界使用会被阻止或升级。 |

### 4.5 可靠性与恢复

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| REQ-REC-01 | 已确认的需求、决策、任务历史和恢复事实在进程重启后不得丢失。 | P0 | 重启演练后可以继续查看并处理原有工作。 |
| REQ-REC-02 | 系统必须区分可安全重试、已过期和结果未知三类情况。 | P0 | 过期工作被拒绝；瞬时失败可重试；未知结果进入人工核对。 |
| REQ-REC-03 | 恢复过程不得生成重复的业务效果。 | P0 | 重放或重启不会重复创建任务、重复合并或重复记录同一决策。 |
| REQ-REC-04 | 网络中断或模型服务不可用时，已提交的工作必须有明确状态。 | P0 | 用户能区分等待恢复、可重试和需要重新确认的工作。 |
| REQ-REC-05 | 系统必须提供可审计的事实历史，支持解释状态如何形成。 | P0 | 对任一交付可重建需求、任务、决策、尝试和异常的因果链。 |
| REQ-REC-06 | 备份或恢复失败必须被显式报告，不能伪装成已保护。 | P1 | 用户能看到最近一次成功保护点和恢复验证结果。 |

### 4.6 交付与反馈

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| REQ-DEL-01 | 交付前必须汇总需求验收、自动检查、互审结果、人工决策和剩余风险。 | P0 | 用户可在一个交付摘要中判断是否批准。 |
| REQ-DEL-02 | 未满足强制验收条件或存在未解决高风险时，不得标记为完成。 | P0 | 系统明确阻塞原因和解除条件。 |
| REQ-DEL-03 | 交付结果必须能关联回需求版本和任务产出。 | P0 | 交付记录能回答“交付了哪个目标、由哪些工作构成”。 |
| REQ-DEL-04 | 交付后的反馈必须能回流到原需求或创建有来源的新需求。 | P1 | 反馈不会成为无法处理的孤立信息。 |

## 5. 非功能需求

| ID | 领域 | 要求 | 优先级 |
|---|---|---|---:|
| NFR-01 | 人的控制权 | 所有改变目标、范围、交付或未知副作用的动作都可暂停并等待人确认。 | P0 |
| NFR-02 | 可解释性 | 系统展示的状态、推荐和自动动作都能链接到事实、规则或先例。 | P0 |
| NFR-03 | 本地优先 | 核心需求、任务、决策、记忆和审计在本机可用；外部模型不可用时不应丢失已提交事实。 | P0 |
| NFR-04 | 可恢复性 | 常见进程、机器、网络和 provider 故障有明确恢复路径，恢复结果可验证。 | P0 |
| NFR-05 | 一致性 | 并发、迟到和重复消息不能产生相互矛盾的需求、任务或决策终态。 | P0 |
| NFR-06 | 性能 | 日常单用户操作应保持可交互；耗时的 agent、检查和记忆处理不能阻塞注意力界面。 | P0 |
| NFR-07 | 隐私 | 凭据和项目内容只在用户明确授权的范围内发送到外部服务；敏感内容不会被无意展示到其他项目。 | P1 |
| NFR-08 | 可维护性 | 需求、架构、模块和测试之间保持可追踪；修改一个领域概念时能定位受影响文档。 | P0 |
| NFR-09 | 单用户边界 | 首期不要求多租户、多人权限和跨组织协作；不得为未承诺的规模引入复杂性。 | P0 |

除非另有需求 ID，本文不规定具体吞吐、机器数量、数据库产品或编程语言。性能目标应在对应用户场景和真实负载下补充测量基线，而不是在需求阶段凭空承诺实现数字。

## 6. 核心验收指标

以下指标用于判断系统是否降低了产品所有者的注意力成本。指标必须能从系统事实和用户操作记录计算；队列吞吐、重试次数和恢复耗时属于支撑指标。

| 指标 | 定义 | 首期观察方式 |
|---|---|---|
| 人工审查时间 / 交付 | 用户实际打开并处理决策项的时间总和 | 按每次交付统计，观察滚动中位数 |
| 需求漂移提前发现率 | 交付前发现的漂移 ÷ 全部发现的漂移 | 按月观察，区分发现阶段和发现来源 |
| 先例自动处理率 | 满足条件并自动采用的先例 ÷ 所有先例决策 | 按月观察，并抽查错误自动采用 |
| 人的决策次数 / 交付 | 一次交付中需要产品所有者明确选择的次数 | 按需求版本聚合 |
| 交付可追溯率 | 能完整回溯需求、任务、决策和证据的交付 ÷ 全部交付 | 每次交付验收 |

指标用于反馈设计，不构成让系统自动压缩人工审查的理由。安全性、解释性和人的最终权威优先于指标优化。

## 7. 明确不做

以下内容不属于首期需求，除非新增需求并重新评审：

- 不建设面向多人组织的权限、租户、计费和组织管理系统。
- 不让 agent 独立完成付款、签约、报税、生产数据删除等不可逆外部动作。
- 不以“更多 agent”“更高队列吞吐”作为产品成功标准。
- 不把原型、设计稿或 agent 日志当作需求本身；需求必须由目标和验收条件定义。
- 不要求原型与最终实现长期并存，也不把假数据能力当作生产能力。
- 不在需求阶段规定迁移工具、ORM、队列产品、HTTP 框架或 agent 编排框架。
- 不因为支持某个技术选型而新增用户价值；技术选型必须服务于已有需求。

## 8. 追踪与变更

### 8.1 文档关系

| 文档 | 负责回答的问题 | 权威范围 |
|---|---|---|
| `requirements.md` | 为什么做、做什么、何时完成 | 产品目标、范围、需求和验收 |
| `architecture.md` | 如何组织系统能力 | 分层、领域协作和架构权衡 |
| `MODULES-DESIGN.md` | 模块如何分责 | 模块边界、依赖方向和所有权 |
| `QUEUE-DESIGN.md` | 支撑执行如何可靠恢复 | 队列语义、投递和恢复边界 |
| `db/schema.sql` | 当前初始数据结构是什么 | 初始建表 SQL |

当文档之间冲突时，先检查是否把实现决策误写成需求；产品需求的变更必须先更新本文，再同步架构和模块设计。

### 8.2 需求变更记录

每次需求变更至少记录：

- 变更原因和提出者；
- 受影响的需求 ID 与版本；
- 受影响的在途任务、决策和交付；
- 验收条件的新增、删除或改变；
- 产品所有者的确认结果。

当前版本没有预设迁移流程或运行时实现。进入开发阶段后，再根据稳定的需求和架构边界定义实现计划。
