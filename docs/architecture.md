# Sinan 架构设计

> **架构基线**：本文件根据 [`requirements.md`](requirements.md) 定义系统如何组织能力，不重新定义产品需求。
> **文档性质**：逻辑架构、职责边界、领域协作、可靠性语义和架构验收标准。
> **明确禁止**：本文不包含可执行代码、SQL、迁移脚本、运行时实现、具体供应商 API 调用或部署脚本。
> **版本**：v0.1 ｜ **状态**：首期架构基线 ｜ **更新**：2026-09-02

## 1. 架构评审规则

架构评审必须遵循以下规则：

1. 先验证需求价值闭环，再评估支撑能力；队列、数据库和运行时不能成为主叙事。
2. 每个架构决策必须引用一个或多个需求 ID；不能回指需求的内容不进入基线。
3. 架构只定义职责、依赖方向、协作协议、状态语义和不变量；实现细节移交模块设计或开发文档。
4. 需求、架构、模块和实现分层维护：需求回答“做什么”，架构回答“如何组织”，模块设计回答“谁负责”，代码回答“如何实现”。
5. 任何自动动作都必须保留人的最终控制权、可解释性和撤销或升级路径。
6. 任何状态都必须有唯一事实来源；跨层复制只能是派生视图，不能形成第二个权威状态。
7. 需求版本发生变化时，必须重新检查在途工作、验收条件、决策和交付血缘；禁止静默兼容旧目标。
8. 架构验收以用户场景和可观察结果为准，不以“代码量”“组件数量”或“并行 agent 数量”为成功标准。

### 1.1 评审优先级

| 优先级 | 评审对象 | 判断问题 |
|---|---|---|
| **CORE** | 意图治理、需求血缘、协作收敛、注意力路由、先例复用 | 是否直接决定产品价值闭环能否成立？ |
| **ENABLEMENT** | 状态一致性、持久化、执行边界、事件传递、恢复能力 | 缺失是否使核心闭环无法可信运行或验证？ |
| **HARDENING** | 吞吐、备份便利性、运维自动化、扩展并行度 | 是否只是增强，而不改变核心闭环？ |

评审顺序固定为 **CORE → ENABLEMENT → HARDENING**。支撑层问题只有在影响核心验收时才能提升优先级。

### 1.2 需求追踪规则

架构章节使用需求 ID 作为锚点。至少应覆盖：

- `REQ-INT-*`：意图、需求版本和漂移治理；
- `REQ-COL-*`：任务、产出、并行协作和收敛；
- `REQ-ATT-*`：人的决策、注意力排序和最终权威；
- `REQ-MEM-*`：记忆、先例和适用边界；
- `REQ-REC-*`：故障分类、审计和恢复；
- `REQ-DEL-*`：交付摘要、阻塞和反馈闭环；
- `NFR-*`：控制权、解释性、本地优先、一致性、性能、隐私和可维护性。

没有需求 ID 的架构内容只能作为待评估选项，不得作为已决定约束。

## 2. 架构目标与边界

### 2.1 目标

Sinan 为一人公司提供一条从模糊意图到可交付产品的可追踪协作链：

```text
意图 → 澄清与验证 → 版本化需求 → 任务协作
     → 产出验证与收敛 → 人的决策 → 交付
     → 决策与经验复用
```

架构的首要目标不是让 agent 尽可能多地并行，而是：

- 让产品所有者始终知道系统正在服务哪个目标；
- 让需求变化可以计算地影响在途工作；
- 让多个 agent 的产出在合并前收敛为可审查证据；
- 让人只处理真正需要判断的事项；
- 让已经确认的决策成为下一次工作的可解释先例；
- 让崩溃、断网和未知结果不会破坏上述闭环。

### 2.2 系统边界

**系统内**：意图和需求治理、原型协作、任务派生、agent 执行协调、产出验证、决策路由、记忆与先例、交付摘要、事件审计和本机恢复。

**系统外**：模型供应商、Git 工具本身、外部部署平台、最终产品的运行时业务、付款/签约/报税等不可逆动作。系统只记录和治理这些边界上的请求、结果和未知状态，不伪装成外部系统的权威。

**首期部署边界**：单用户、local-first、单机运行。多用户权限、多租户、计费、跨组织协作不属于首期架构目标，见 `requirements.md` §7。

### 2.3 参与者与权威

| 参与者 | 责任 | 不可越过的边界 |
|---|---|---|
| 产品所有者 | 确定目标、取舍、需求版本和交付 | 任何 agent 或自动规则都不能代替最终确认 |
| agent | 产生澄清、原型、实现、验证和审查意见 | 只能在已授权任务、范围和契约内行动 |
| Sinan | 保存事实、协调任务、路由注意力、发现漂移、恢复状态 | 不得隐式改变目标、吞掉分歧或确认未知外部副作用 |
| 外部服务 | 提供模型、代码托管或部署能力 | 其可用性和结果不能成为本地事实的唯一来源 |

## 3. 总体逻辑架构

### 3.1 分层图

```text
┌─────────────────────────────────────────────────────────────┐
│  体验与注意力层                                             │
│  需求确认 · 原型反馈 · 决策入口 · 交付摘要 · 工位视图       │
├─────────────────────────────────────────────────────────────┤
│  治理与领域协作层                                           │
│  意图澄清 · 需求版本 · 任务派生 · 验证收敛 · 决策 · 交付    │
├─────────────────────────────────────────────────────────────┤
│  协作与执行层                                               │
│  agent 编排 · 工作范围 · 契约协作 · worktree · 工具边界    │
├─────────────────────────────────────────────────────────────┤
│  记忆与证据层                                               │
│  决策先例 · 约定 · 失败经验 · 需求/任务/产出关联 · 召回     │
├─────────────────────────────────────────────────────────────┤
│  持久化与恢复基础层                                         │
│  事实记录 · 可靠投递 · 租约与过期 · 副作用状态 · 启动对账  │
├─────────────────────────────────────────────────────────────┤
│  外部边界                                                   │
│  模型 provider · Git · 测试/构建工具 · 部署平台             │
└─────────────────────────────────────────────────────────────┘
```

这是逻辑分层，不要求一层对应一个进程或一个包。首期允许治理、协作、记忆和恢复运行在同一常驻服务中；分层的意义是限制责任和依赖，而不是制造部署复杂度。

### 3.2 依赖方向

依赖只能向下或通过定义好的协议边界流动：

```text
体验与注意力 → 治理领域 → 协作/执行、记忆、持久化恢复
外部适配器 ───────────────────────────────┘
```

- 体验层不能直接写领域事实或调用外部模型。
- 治理层拥有需求、任务、决策和交付语义，但不拥有具体 agent 工具实现。
- 协作/执行层提供受约束的工作能力，不决定需求目标和最终交付。
- 记忆层提供有来源的事实与先例，不直接改变任务状态。
- 持久化/恢复层提供可靠性原语，不接管产品领域决策。
- 外部适配器只能通过边界契约接入；供应商更换不应改变核心领域模型。

## 4. 领域模型

架构用以下概念连接需求、协作和证据。概念是业务语义，不是数据库表或代码类。

| 概念 | 语义 | 关键关系 |
|---|---|---|
| **意图** | 产品所有者最初表达的愿望、问题或方向 | 可产生一个或多个需求草稿 |
| **需求** | 经确认的目标、原因、范围、不做事项和验收条件 | 具有版本；是任务与交付的根 |
| **原型** | 用于验证交互/视觉方向的可运行、可丢弃产物 | 反馈必须回指意图或需求 |
| **任务** | 为满足某个需求版本而承担的有限工作 | 有产出、完成条件、依赖和影响范围 |
| **产出** | 原型、代码、设计规格、测试证据或交付包 | 必须能回指任务和需求验收条件 |
| **决策项** | 需要产品所有者选择的阻塞、分歧或高风险事项 | 带来源、选项、影响和证据 |
| **决策事实** | 人最终选择及其理由、影响和时间 | 可沉淀为先例 |
| **先例** | 在明确条件下可复用的已确认决策或经验 | 低置信度或越界时必须升级 |
| **反馈** | 交付后或原型阶段观察到的结果、问题和新信息 | 回流到既有需求或形成有来源的新意图 |
| **操作结果** | 对外部系统或不可逆动作的已知、失败或未知结果 | 未知结果不能被自动解释为成功/失败 |

### 4.1 领域不变量

以下不变量属于架构契约，具体数据结构由实现阶段决定：

1. 未经产品所有者确认的需求不能产生可执行任务。
2. 每个任务、决策、产出和交付都能追溯到需求及其版本；没有血缘的事实必须被标记为待归属。
3. 需求内容按版本保留历史；新版本不得静默覆盖旧目标。
4. 需求变更必须显式决定在途任务继续、重新派生、暂停或放弃。
5. 一个任务在同一时刻只有一个有效执行尝试；历史尝试可以保留。
6. 任务“执行完成”不等于“交付完成”；验证、互审和人的确认必须有独立语义。
7. 任何自动采用的先例都能展示来源、适用条件、置信依据和回退方式。
8. 决策项在解决前必须可见；解决后必须记录结果及其影响，不能删除阻塞痕迹。
9. 状态变化、重要输入、决策和副作用结果形成可审计事实链。
10. 迟到、重复或过期的执行结果不得回写到更新后的需求或已关闭工作。

## 5. 分层职责设计

### 5.1 体验与注意力层

**服务需求**：`REQ-INT-03`、`REQ-ATT-01` 至 `REQ-ATT-06`、`REQ-DEL-01` 至 `REQ-DEL-03`、`NFR-01`、`NFR-02`、`NFR-06`。

**职责**：

- 呈现待确认的需求草稿、原型反馈、决策项和交付摘要；
- 将阻塞成本、紧迫性和影响范围转化为可解释的注意力顺序；
- 记录用户实际打开、查看和处理决策的行为；
- 订阅领域状态的派生视图，不拥有需求或任务事实；
- 在提交人类选择前展示足够上下文，提交后展示影响范围和后续状态。

**不负责**：需求推理、任务派工、直接执行 agent、改变领域状态、确认未知外部副作用。

### 5.2 治理与领域协作层

**服务需求**：全部 `REQ-INT-*`、`REQ-COL-*`、`REQ-ATT-04/05`、`REQ-MEM-03/04`、`REQ-DEL-*`。

**职责**：

- 管理意图澄清、草稿审议和产品所有者确认；
- 管理需求版本、影响分析、冻结窗口和漂移处理；
- 将需求派生为任务，并在任务完成后组织验证、互审、修订和收敛；
- 创建和解决决策项，解释每个选项会影响哪些任务、需求和交付；
- 在满足条件时组织交付，在不满足条件时保持阻塞；
- 将人工决策和交付反馈交给记忆层形成可复用事实。

**不负责**：直接实现模型调用、Git 操作、数据库恢复、UI 排序算法或外部部署协议。

### 5.3 协作与执行层

**服务需求**：`REQ-COL-01` 至 `REQ-COL-06`、`REQ-DEL-01`、`NFR-01`、`NFR-03`、`NFR-05`。

**职责**：

- 为任务分配受限的 agent 执行上下文和工作范围；
- 隔离并行工作，登记预期影响的文件、接口和共享契约；
- 提供工具调用前的授权、冲突避让和停止边界；
- 收集产出、检查证据和执行结果，交回治理层收敛；
- 将外部工具的已知失败与未知结果区分上报。

**不负责**：自行扩展需求范围、批准合并或交付、把 agent 自述当作验收证据、绕过治理层写入决策。

### 5.4 记忆与证据层

**服务需求**：`REQ-MEM-01` 至 `REQ-MEM-05`、`REQ-INT-02`、`REQ-INT-04`、`REQ-ATT-02`、`REQ-REC-05`。

**职责**：

- 保存有来源的决策、约定、事实、失败经验和适用范围；
- 根据需求、任务、契约和当前上下文提供相关记忆；
- 返回证据、来源和适用边界，而不是无来源的结论；
- 记录先例被采用、被拒绝、失效或升级的结果；
- 为交付和漂移检查提供可回溯的事实材料。

**不负责**：替产品所有者作最终决定、修改需求版本、直接派工或把相似文本直接视为适用先例。

### 5.5 持久化与恢复基础层

**服务需求**：`REQ-REC-01` 至 `REQ-REC-06`、`NFR-03` 至 `NFR-05`。

**职责**：

- 持久化已确认事实、领域状态、执行游标和副作用结果；
- 可靠传递领域事件和执行工作，支持重复投递和安全去重；
- 为执行尝试提供租约、过期识别和迟到结果拒绝语义；
- 在启动或异常后执行对账，恢复可继续、可重试、需核对或需重做的状态；
- 提供审计事实的连续性和备份/恢复状态可见性。

**不负责**：定义产品状态机、选择决策选项、判断先例置信度或改变人的选择。

可靠性语义以 [`QUEUE-DESIGN.md`](QUEUE-DESIGN.md) 为支撑层权威；本文只规定它必须服务于哪些领域不变量。

### 5.6 外部边界层

**服务需求**：`NFR-03`、`NFR-07`、`REQ-REC-02`、`REQ-REC-04`。

**职责**：

- 将模型、Git、测试/构建和部署能力适配为受约束的内部能力；
- 传递请求上下文、授权范围、超时、已知结果和未知结果；
- 在外部服务不可用时不丢失本地已提交事实；
- 让供应商替换只影响适配边界，不扩散到领域模块。

**不负责**：保存 Sinan 的领域权威状态、决定重试策略或直接通知产品所有者。

## 6. 模块设计

模块是职责边界，不是当前代码目录的承诺。具体目录和包拆分见 [`MODULES-DESIGN.md`](MODULES-DESIGN.md)，实现前不得根据本节直接生成代码。

### 6.1 核心模块

| 模块 | 所属层 | 主要职责 | 允许依赖 | 明确不做 |
|---|---|---|---|---|
| **意图治理** | 治理 | 澄清、草稿审议、确认、原型反馈归属 | 记忆、可靠性、执行能力 | 直接创建未经确认的执行工作 |
| **需求管理** | 治理 | 版本、影响分析、冻结、漂移、血缘 | 意图治理、任务协作、记忆 | 静默覆盖历史需求 |
| **任务协作** | 治理/协作 | 派生任务、依赖、契约责任、收敛编排 | 需求、执行、可靠性 | 直接批准最终交付 |
| **执行适配** | 协作/执行 | agent 会话、工作范围、工具安全、产出回传 | 可靠性、外部边界、Git | 改变需求和决策 |
| **验证与审议** | 治理 | 机器检查、独立互审、证据汇总、分歧升级 | 任务、记忆、执行 | 以自述替代证据 |
| **决策管理** | 治理/注意力 | 决策项、选项、影响、结果和后续动作 | 需求、任务、记忆、可靠性 | 代替人确认高风险动作 |
| **先例与记忆** | 记忆 | 存储、召回、适用性和先例生命周期 | 可靠性 | 无来源自动建议 |
| **交付管理** | 治理 | 交付门槛、摘要、发布确认、反馈入口 | 验证、决策、需求、外部边界 | 绕过未解决阻塞 |
| **注意力视图** | 体验 | 待决策排序、工位状态、审查计时、交付摘要呈现 | 领域只读视图、事件订阅 | 写入领域事实 |
| **可靠性内核** | 持久化/恢复 | 事件、工作投递、租约、恢复、审计连续性 | 本地存储、外部边界的通用协议 | 业务状态机和产品决策 |
| **边界适配** | 外部边界 | 模型、Git、构建、部署和 HTTP/SSE 适配 | 可靠性、协议定义 | 将外部 API 暴露给领域层 |

### 6.2 模块协作规则

1. 模块通过领域命令、事实事件或只读查询协作，不直接修改其他模块拥有的事实。
2. 每个事实集合有唯一写入责任方；其他模块只能通过责任方的抽象能力提出变更。
3. 可靠性内核只保证投递和恢复语义，不解释业务事件的含义。
4. 注意力视图是派生读模型；它延迟或重建不会改变领域事实。
5. 记忆是证据提供者，不是第二个需求或任务数据库。
6. 外部边界返回结果分类，不把供应商错误类型泄漏到核心领域模型。
7. 跨模块协作必须带需求血缘和因果上下文；无法关联时显式进入待归属状态。

### 6.3 模块所有权摘要

| 事实类别 | 唯一责任模块 | 其他模块可做的事 |
|---|---|---|
| 意图与需求版本 | 意图治理 / 需求管理 | 提交澄清、反馈和变更提议 |
| 任务、依赖和产出收敛状态 | 任务协作 / 验证与审议 | 报告执行结果、提出重做或升级 |
| 执行尝试、租约和外部操作结果 | 执行适配 / 可靠性内核 | 请求认领、续租、关闭或核对 |
| 决策项与人工决策 | 决策管理 | 提供证据、选项和影响分析 |
| 记忆与先例 | 先例与记忆 | 查询、引用、反馈适用性 |
| 注意力排序和审查计时 | 注意力视图 | 读取派生视图、提交用户动作 |
| 审计事实和恢复屏障 | 可靠性内核 | 查询恢复状态、报告边界结果 |

## 7. 核心流程架构

流程描述的是跨模块责任和状态语义，不是实现步骤。

### 7.1 意图到需求

```text
产品所有者提出意图
        ↓
意图治理识别目标、why、范围、反例和验收条件
        ↓
可选：原型验证交互/视觉方向
        ↓
结构化审议与分歧呈现
        ↓
产品所有者确认 / 驳回 / 继续澄清
        ↓
需求管理形成新版本，建立血缘和变更影响
```

约束：

- 具体方案只能作为候选路径，不能直接成为需求目标（`REQ-INT-01`）。
- 草稿未确认时不得进入可执行任务（`REQ-INT-03`）。
- 原型反馈必须回到对应意图或需求；原型可丢弃，但反馈不能丢失（`REQ-INT-05`）。

### 7.2 需求到任务

```text
已确认需求版本
        ↓
需求管理分析范围、验收条件和在途工作影响
        ↓
任务协作派生任务、依赖、产出类型和影响范围
        ↓
协调层分配授权工作范围
        ↓
执行适配接收任务并回传产出/证据/异常
```

任务派生必须是可解释的：每个任务说明服务哪个目标、使用哪个需求版本、完成什么、依赖什么、可能影响什么（`REQ-COL-01`）。需求变更时，旧任务不能继续以“最新”名义运行，必须按影响分析选择继续、重新派生、暂停或放弃（`REQ-INT-06`）。

### 7.3 产出到交付

```text
执行产出
   ↓
适用的机器验证
   ↓
独立 agent 互审
   ├─ 通过且证据完整 ─→ 先例/规则检查
   ├─ 需要修改 ───────→ 返回任务重做
   └─ 分歧/低置信/高风险 ─→ 决策入口
                                ↓
                         产品所有者选择
                                ↓
                         合并/发布/暂停/放弃
```

“执行完成”“验证通过”“互审通过”“合并完成”“交付批准”是不同事实。交付管理只有在强制验收条件满足、风险已处理、必要决策已解决时才允许形成交付候选（`REQ-DEL-01`、`REQ-DEL-02`）。

### 7.4 决策与注意力

所有需要人判断的事项进入统一决策模型：

1. 产生来源：需求冲突、任务分歧、低置信先例、未知副作用或交付确认；
2. 携带上下文：相关需求版本、任务、产出、证据和已知风险；
3. 提供有限且互斥的动作：继续、修改、重新派生、暂停、放弃、确认或核对；
4. 说明影响：哪些任务、需求版本、交付和记忆会被改变；
5. 记录结果：谁在何时做出选择，以及选择产生的后续事实。

注意力视图按阻塞成本和紧迫性排序，但排序不能隐藏低优先级事项，也不能改变决策语义（`REQ-ATT-01` 至 `REQ-ATT-05`）。

### 7.5 先例复用

```text
当前决策上下文
        ↓
记忆层返回相关先例 + 来源 + 适用条件 + 置信信息
        ↓
适用性判定
        ├─ 条件满足且置信度足够 → 可自动采用并记录
        └─ 条件不足/冲突/低置信 → 升级产品所有者
        ↓
决策结果反馈到任务、需求和先例生命周期
```

自动采用不是“相似即通过”。适用性必须同时考虑需求上下文、项目/用途边界、先例状态、冲突记录和人工撤销路径（`REQ-MEM-02`、`REQ-MEM-03`）。人工决策完成后，只有包含适用条件和结果的决策事实才能沉淀为先例（`REQ-MEM-04`）。

### 7.6 需求变化与漂移

需求变化和漂移检测共享同一条治理路径：

- 识别变化触及目标、why、范围、验收条件还是表述；
- 列出受影响的任务、产出、决策和交付；
- 对在途工作提出继续、重新派生、暂停或放弃；
- 对已产出内容进行目标一致性检查；
- 在合并和交付前阻止未解决的漂移；
- 将人的选择和最终影响记录为决策事实。

漂移不能只作为告警日志存在，必须成为可处理的决策项或明确的任务动作（`REQ-INT-06`、`REQ-DEL-02`）。

### 7.7 故障与恢复

恢复层向治理层提供四类稳定语义：

| 结果类别 | 领域含义 | 后续动作 |
|---|---|---|
| **已确认成功** | 事实已落地，可继续后续流程 | 继续收敛或交付 |
| **可安全重试** | 没有不可逆未知副作用 | 按策略重新执行 |
| **已过期/迟到** | 结果属于旧尝试或旧需求 | 拒绝写入，不触发业务重试 |
| **结果未知** | 外部副作用可能已发生 | 停止自动重试，进入人工核对 |

进程或机器恢复时，系统先恢复事实连续性，再恢复可执行工作；恢复过程不得覆盖已确认的需求和决策，也不得将未知操作自动标记为成功或失败（`REQ-REC-01` 至 `REQ-REC-05`）。

## 8. 状态与协议边界

### 8.1 状态分层

状态按事实归属分为三类，避免“一个状态字段承载所有语义”：

| 状态域 | 表达什么 | 由谁解释 |
|---|---|---|
| 领域状态 | 需求、任务、决策和交付处于哪个业务阶段 | 治理与领域模块 |
| 执行状态 | 某次 agent/工具尝试是否排队、运行、完成、失败或未知 | 执行与可靠性模块 |
| 视图状态 | 用户是否已看到、打开或处理某项注意力 | 注意力模块 |

执行状态不能替代领域状态；视图状态不能反推用户已经批准业务动作。

### 8.2 事实事件

跨模块事实事件至少携带：

- 事件唯一身份和事件类别；
- 需求/任务/决策等聚合归属；
- 端到端关联上下文和直接因果来源；
- 产生时间、来源模块和结果分类；
- 与执行尝试或外部操作的关联；
- 可审计的业务载荷。

事件是事实通知，不是隐式命令。事件消费者必须能识别重复、迟到、未知和不适用结果；事件协议的完整目录和可靠投递语义由 `QUEUE-DESIGN.md` 维护。

### 8.3 查询与写入边界

- 领域模块通过拥有者定义的命令改变事实；不能跨模块直接写存储。
- 视图模块只读领域事实和审计事实，并维护可重建的派生视图。
- 记忆引用必须带来源和适用范围；召回结果不能直接改变任务或需求。
- 外部边界必须把请求和结果交给可靠性内核记录；未知结果必须回到决策管理。

## 9. 可靠性架构约束

可靠性是核心价值的保护层，而不是第二套业务架构。

### 9.1 持久化边界

本地权威事实包括：已确认需求及版本、任务和依赖、决策项及结果、产出索引、先例、执行尝试、外部操作结果和恢复审计。进程内缓存、UI 状态和 checkpoint 都是可丢弃或可重建的派生信息。agent 上下文可以由外部执行适配器持久化（首期 Pi 使用 per-actor JSONL session），但它不是领域状态或审计事件的权威来源；领域状态必须仍能从 SQLite 事实和事件恢复。

### 9.2 幂等与重放

- 业务事实写入必须能识别重复输入，重复投递不得重复产生业务效果。
- 事件投递可以至少一次，但每个消费者必须有业务幂等边界。
- 事实历史必须足以解释状态如何形成；checkpoint 只能加速恢复，不能成为唯一事实。
- 需求、任务和决策的重复创建、重复关闭和重复交付必须被拒绝或转为已处理结果。

### 9.3 租约与迟到结果

每个执行尝试都有明确的有效期和版本化授权。授权失效后，旧 agent 的迟到结果只能被识别和记录，不能回写当前任务。失效拒绝不是可重试异常，避免旧工作阻塞新工作。

### 9.4 未知副作用

Git 推送、部署、外部 API 和其他不可逆动作必须允许出现“请求已发出但结果未知”。未知状态进入注意力队列，要求产品所有者核对后才能继续；系统不能通过盲目重试“猜测”外部世界。

### 9.5 恢复验收

架构必须支持以下场景的可验证结果：进程崩溃、机器异常重启、睡眠唤醒、网络中断、模型服务超时、执行器失联、重复事件、迟到结果和备份恢复。每个场景都要给出继续、重试、拒绝、核对或重做中的明确状态。

队列内核的具体恢复语义、初始数据结构和实现边界分别见 [`QUEUE-DESIGN.md`](QUEUE-DESIGN.md) 与 [`db/schema.sql`](db/schema.sql)；这些文档不能反向改变本节的领域责任。

## 10. 安全、隐私与性能边界

### 10.1 人的控制权

改变需求目标、范围、交付状态或未知副作用的动作必须可暂停并等待产品所有者。系统可以自动执行低风险、可逆且满足先例条件的动作，但必须保留来源、条件和撤销/升级路径（`NFR-01`）。

### 10.2 可解释性

用户看到的推荐、排序、状态和自动动作必须能链接到需求、规则、证据、先例或恢复事实。原始 agent 日志可以作为证据，但不能是唯一解释（`NFR-02`、`REQ-ATT-02`）。

### 10.3 本地优先与隐私

本地保存需求、决策、任务、记忆和审计事实；外部模型只接收明确授权范围内的上下文。凭据、项目内容和不同用途的记忆必须有边界。外部服务不可用时，本地已提交事实仍可查看和治理（`NFR-03`、`NFR-07`）。

### 10.4 性能

日常单用户操作和注意力界面必须保持可交互；agent 调用、验证、构建和记忆处理不能阻塞用户界面。具体吞吐、延迟和机器配置不在本架构阶段凭空承诺，进入实现阶段后以真实场景建立基准（`NFR-06`）。

## 11. 部署与技术决策边界

首期采用单机、单用户、local-first 的部署形态：一个主要服务进程、一个本地权威数据存储、受控的 agent/工具子进程和浏览器界面。是否使用 Node.js、SQLite、SSE、Pi 或 `sqlite-vec` 属于技术选型文档的责任；本架构只约束它们必须满足的边界：

- 本地事实可持久化、可审计和可恢复；
- agent 执行与领域治理隔离；
- 记忆召回返回来源和适用条件；
- UI 通过稳定协议读取视图并提交用户动作；
- 替换某个 provider 不改变需求、任务和决策语义。

技术选型和依赖基线见 [`TECH-STACK.md`](TECH-STACK.md) 与 [`docs/dependencies.md`](docs/dependencies.md)，模块包边界见 [`MODULES-DESIGN.md`](MODULES-DESIGN.md)。这些文档不得新增未被需求支持的产品能力。

## 12. 架构验收与追踪

### 12.1 价值闭环验收

| 验收主题 | 必须证明的结果 | 主要需求 |
|---|---|---|
| 意图治理 | 方案会回退到目标；未经确认不能开工；why 和验收条件可见 | `REQ-INT-01`～`REQ-INT-03` |
| 需求血缘 | 版本可比较；变化会影响在途任务；没有静默旧工作 | `REQ-INT-04`～`REQ-INT-06` |
| 协作收敛 | 并行工作隔离；冲突可见；产出有验证和互审证据 | `REQ-COL-01`～`REQ-COL-06` |
| 注意力路由 | 所有需人事项集中、可解释、按阻塞成本排序 | `REQ-ATT-01`～`REQ-ATT-06` |
| 先例复用 | 先例有来源和条件；低置信或冲突时升级；人工决策可沉淀 | `REQ-MEM-01`～`REQ-MEM-05` |
| 交付追踪 | 交付摘要汇总证据、决策、风险和需求版本；反馈可回流 | `REQ-DEL-01`～`REQ-DEL-04` |

### 12.2 可靠性验收

| 场景 | 架构必须保证 |
|---|---|
| 进程/机器重启 | 已确认事实不丢失；可继续工作或明确等待核对 |
| 网络/模型超时 | 区分可重试与未知；未知副作用不自动重做 |
| 重复/迟到事件 | 不重复产生业务效果；旧结果不能污染新需求或新尝试 |
| 执行器失联 | 有效期结束后可回收；旧执行器不能继续写入 |
| 备份恢复 | 恢复点、缺失事实和验证结果对用户可见 |

对应 `REQ-REC-01`～`REQ-REC-06`、`NFR-03`～`NFR-05`。

### 12.3 设计完成的定义

本架构在进入实现前必须满足：

- 每个 P0 需求都有唯一责任层和至少一个责任模块；
- 每个跨模块流程都定义输入事实、输出事实、人的介入点和失败出口；
- 需求、任务、决策、先例和交付之间的血缘不会断裂；
- 领域状态、执行状态和视图状态没有混用；
- 可靠性层的语义不会取代产品治理；
- 任何实现候选都能在不改变需求的情况下被替换；
- 架构文档没有可直接运行的实现代码，初始 SQL 只存在于 [`db/schema.sql`](db/schema.sql)。
